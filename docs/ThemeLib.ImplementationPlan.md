# ThemeLib 拆分与多控件库主题协调实施方案

## 1. 结论与目标

将现有主题能力抽取到 `Wpf.Zen.Ui.ThemeLib` 可行。实施目标是建立独立的主题基础设施，而不是只移动主题文件。

完成后应支持：

1. 应用只引用 ThemeLib，使用主题状态及默认语义资源，自行实现控件。
2. VirtualInput 只依赖 ThemeLib，不通过直接或传递引用加载 Wpf.Zen.Ui。
3. Wpf.Zen.Ui 依赖 ThemeLib，负责现有控件及其视觉风格。
4. 多个控件库提供自己的主题资源，共享系统跟随、明暗、高对比度和强调色状态。
5. 保留局部主题、无 Application 宿主、Popup 和多 STA 场景的既有能力与失败降级。

本文件是实施设计，不表示拆分已经完成。接口名称属于建议稿，应在验证阶段收敛；不要求保留旧 API 的兼容层。

## 2. 当前实现与迁移前提

当前存在以下实际耦合：

| 位置 | 当前行为 | 实施影响 |
| --- | --- | --- |
| `Appearance/ThemeManager.cs` | 写死主库主题 URI，加载全局资源及原生控件样式 | 主题状态协调与具体资源组合需要分离 |
| `Appearance/ThemeManagerOptions.cs` | 只有一组 AdditionalLight/Dark/HighContrast 入口 | 应用覆盖与多个库的资源注册需要分别表达 |
| `Resources/GlobalResources.xaml` | 引用 FocusVisualPresenter | 不能整体移入纯主题库 |
| `ThemeResourceAnchor.cs` | 触发 LibraryInitializer | 资源键必须解除控件初始化副作用 |
| `LibraryInitializer.cs` | 初始化 TextBlock 元数据和 Popup 行为 | 留在控件库，ThemeLib 不承担这些策略 |
| `Appearance/SystemThemeResourceHost.cs` | 管理 PresentationFramework 和现有主库的资源槽位 | 需要验证并扩展跨程序集资源路由 |
| VirtualInput 的 `Themes/Generic.xaml` | 使用 Button、DynamicScrollViewer、ScrollViewerAssist、IconPresenter 和 FluentIconSource | 只移动主题不能解除主库依赖 |
| VirtualInput 的 `Layouts/Internal/KeyboardLayoutParts.cs` | 使用 FluentIconSource 和 SymbolRegular | 内置图标表示需要独立化 |

当前主题切换已经区分调色板和结构性样式。该设计意图应保留：普通明暗切换不应因重新创建模板而丢失输入、焦点、Popup 或动画状态。

## 3. 项目边界

```text
Wpf.Zen.Ui.ThemeLib
    ↑                  ↑                       ↑
Wpf.Zen.Ui      Wpf.Zen.Ui.VirtualInput     其他风格控件库
```

箭头表示上层库依赖 ThemeLib。ThemeLib 不反向引用任何控件库。

### 3.1 ThemeLib

负责：

- 主题偏好、有效明暗状态、高对比度状态、强调色来源。
- 系统事件监听、更新调度和变更通知。
- 全局与局部主题资源协调。
- 模块契约、注册校验、依赖排序和资源构建。
- Application 资源宿主及无 Application 宿主的适配。
- 共享语义资源键和相应资源引用扩展。
- 可显式选用的内置默认语义资源模块，支持仅引用 ThemeLib 的使用方式。
- 主题机制实际需要的内部辅助代码，不整体搬迁主库工具类。

默认语义资源模块与管理器在职责上分离。其他风格库可以选择复用共享语义资源，也可以采用自己的私有资源；管理器不强制所有模块使用 Zen 的颜色层级或强调色算法。

### 3.2 Wpf.Zen.Ui

负责控件、行为、模板、图标呈现、控件专属资源键及 Zen 视觉资源模块。原生 WPF 控件的隐式样式和全局焦点样式作为显式选用的资源入口提供。

仅初始化 ThemeLib，不应自动改写原生控件样式、元数据或 Popup 交互策略。

### 3.3 VirtualInput

保留键盘、输入与候选词逻辑。其默认模板及内置布局解除主库依赖：

- 使用原生 Button、ScrollViewer 配合键盘自己的模板和必要行为。
- 以键盘本地矢量资源等独立表示承载少量内置图标。
- 替换时核查焦点保持、滚动、禁用状态、自动化和候选交互，不能只改类型名称。
- 优先复用默认语义资源；确有专属颜色等资源时再提供键盘主题模块。

不为减少改动将 Button、图标系统或滚动控件迁入 ThemeLib。也不在本次拆分中预先建立庞大的通用控件基础库。

### 3.4 本次不包含的工作

- 导航或其他大型控件的实际拆包。
- 正式制作第二种完整控件风格。
- 运行时任意切换整套控件设计风格并保证视觉树状态不变。
- 程序集自动扫描发现模块、动态插件卸载等扩展系统。

导航可在本次完成后单独审计依赖，再决定是否直接依赖 ThemeLib。

## 4. 主题状态与模块契约

### 4.1 状态模型

区分用户请求与解析后的状态：

| 数据 | 含义 |
| --- | --- |
| Preference | Light、Dark 或 System 的用户选择 |
| Variant | 当前解析得到的 Light 或 Dark |
| IsHighContrast | 系统是否启用高对比度，独立于明暗偏好 |
| AccentColor | 根据系统、自定义或默认来源解析的强调色 |

局部主题至少允许覆盖明暗偏好；第一版继续共享系统高对比度与强调色策略，不额外引入局部强调色配置。

高对比度优先于普通明暗调色板。退出高对比度后恢复原来的明暗选择。系统高对比度颜色变化也必须触发更新，不能仅比较布尔状态。

### 4.2 模块描述

建议使用简单的模块描述对象及必要的资源工厂，避免为固定 URI 设计复杂继承体系。

| 字段或能力 | 契约 |
| --- | --- |
| Id | 稳定且唯一，用于诊断和重复注册校验 |
| Dependencies | 依赖的模块 ID；缺失和循环依赖在应用资源变更前报错 |
| CommonResources | 与明暗无关的资源入口；结构性资源单独缓存 |
| LightResources / DarkResources | 普通明暗资源入口 |
| HighContrastResources | 使用系统高对比度语义的资源入口 |
| ResourceAssemblies | 无 Application 后端需要覆盖的私有资源键所属程序集；最终形态由验证确定 |
| 可选调色板工厂 | 按主题上下文生成强调色等非结构性资源，不直接修改宿主 |

模块可以只提供公共资源。拥有独立调色板的模块必须提供高对比度映射；完全复用共享资源的模块无需重复声明三套颜色。

资源工厂不得返回由其他 Dispatcher 持有的可变共享字典。不同资源宿主按需要构建独立资源图，只在已验证安全的范围内共享冻结值。

### 4.3 注册方式

由应用在明确的启动边界注册模块。以下仅为表达设计的伪代码，不是已经存在的 API：

```csharp
ThemeManager.Initialize(options =>
{
    options.Modules.Add(DefaultSemanticThemeModule.Instance);
    options.Modules.Add(ZenThemeModule.Instance);
    options.Modules.Add(OtherStyleThemeModule.Instance);
    options.Preference = ThemePreference.System;
});
```

同时提供 XAML 配置入口。应用覆盖字典独立于模块集合表达，不允许不同库通过修改同一组 Additional URI 抢占配置。

第一版优先支持启动时批量注册，不承诺运行时随意增删结构性模块。重复 ID、无效依赖和资源加载失败应提供可定位的异常信息。

## 5. 资源键、优先级与样式规则

### 5.1 资源键归属

- 共享键由 ThemeLib 类型作为 ComponentResourceKey 锚点。
- 模块私有键由所属程序集中的类型作为锚点。
- 不向 ThemeLib 中央枚举持续添加各控件库专属 Token。
- 当前 Color/Brush/Value/Style/Template/Font 键按用途逐项归属，不按文件夹整体搬迁。
- 所有迁移同步修改 XAML 命名空间、pack URI、程序集映射和调用代码。

两个库可共享 Dark 状态而使用不同颜色。模块私有资源不允许靠覆盖共享键来隔离风格；覆盖共享键代表有意改变所有使用该语义的控件。

### 5.2 优先级

管理器拥有的资源容器内，按低到高约定：

```text
默认共享资源 → 按依赖顺序排列的模块资源 → 应用主题覆盖
```

每个模块内部应明确公共资源、当前变体资源和生成调色板的顺序，避免静态 XAML 引用依赖偶然的跨字典加载顺序。

上述规则不改变 WPF 原生优先级。字典自身条目、元素局部资源等仍按 WPF 查找语义生效。管理器只修改自己拥有的容器，不清空用户的 MergedDictionaries。

### 5.3 结构性资源

- 普通切换只替换非结构性的主题值。
- Style、ControlTemplate、DataTemplate 和事件相关结构不作为普通主题覆盖资源。
- 公共结构性资源在同一宿主内保持身份稳定。
- 控件默认模板继续通过各自 Generic.xaml 提供。
- 不同风格库同时为同一个原生 WPF 类型提供全局隐式样式时，应用必须明确选择一个入口，或使用显式样式/局部范围；不声称它们能在同一作用域自动共存。

需要主题变化的引用使用 DynamicResource 或等价扩展；StaticResource 仅用于有意固定的值与结构。

## 6. 更新流程与资源宿主

### 6.1 更新流程

1. 在所属 Dispatcher 上获取主题上下文。
2. 校验模块集合及资源配置。
3. 按模块依赖顺序准备所有目标资源图。
4. 准备失败则保留现有可用资源，报告模块、状态与 URI。
5. 准备成功后提交受管理的资源容器，并完成必要的资源失效通知。
6. 更新已提交的有效状态，发送变更事件。

失败时请求状态与已提交状态的关系必须在 API 中明确，不能通知主题已经成功切换而资源仍然是旧值。原子性主要指提交前准备失败不污染当前资源；跨 Dispatcher 不保证同一瞬间完成，提交阶段异常也需有恢复或降级路径。

### 6.2 Application 宿主

优先使用公开 ResourceDictionary API。局部请求使用明确拥有的资源容器维护覆盖，并验证全局切换后局部明暗选择仍有效。

### 6.3 无 Application 宿主

这是实施前必须通过验证的技术风险。

WPF 系统资源查找按 Type 或 ResourceKey 的所属程序集选择资源字典。不能将所有模块资源只放到 ThemeLib 槽位，然后假定其他程序集的 ComponentResourceKey 都能解析。

需要验证：

- 按模块声明的程序集管理对应资源槽位，避免硬编码 typeof(ThemeVariant).Assembly 作为唯一模块槽位。
- 共享键和模块私有键均可解析，缺失的类型样式仍正常回落到对应 Generic.xaml。
- 原生样式模块未启用时，不引入 Zen 原生样式覆盖。
- 系统主题重置后恢复覆盖，恢复或释放时不破坏原有系统字典。
- 不为创建资源槽位提前加载全部 Generic.xaml。
- 多 STA 下正确处理 WPF 封装、冻结和线程亲和性。
- 反射不可用时沿用并验证现有安全降级，不造成启动或核心界面崩溃。

反射目标、查找缓存、失败行为和依赖条件必须有当前实现视角的注释。框架细节优先依据本地 WPF 官方源码。

## 7. 未初始化与独立使用约定

显式初始化负责系统监听和主题管理。仅加载程序集或访问资源键，不激活全局控件行为。

同时保留可用的静态默认外观：

- ThemeLib 为共享键提供可通过自身 Generic.xaml 等正常 WPF 路径取得的默认资源。
- 各控件库自行提供默认模板与所需私有资源。
- 不在控件模板附近重复合并会遮蔽管理器动态资源的固定调色板。
- 分别验证未初始化、控件先创建后初始化、无 Application 三种路径，最终默认资源组织方式由验证结果确定。

## 8. 实施阶段

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| P0：依赖与行为基线 | 建立资源、初始化、程序集引用清单；运行相关现有测试并记录基线 | 已知依赖与现有失败可区分，保留行为有明确记录 |
| P1：关键机制验证 | 建立最小第二模块及独立资源键程序集；验证 Application/无 Application、多 STA 和默认回退 | 两个模块同时切换且私有键互不干扰，宿主方案可行 |
| P2：在现有项目内引入模块模型 | 分离状态解析、资源组合、宿主；把现有资源包装成模块；拆开应用覆盖入口 | 现有体验保持，管理器不再依赖单组固定主题 URI |
| P3：抽取 ThemeLib | 迁移基础设施和共享资源；调整锚点、命名空间、URI、项目和包引用 | ThemeLib 可单独构建使用，不反向引用主库 |
| P4：VirtualInput 独立化 | 替换主库按钮、滚动和图标依赖；保持键盘必要行为 | 只引用 VirtualInput 的示例不加载 Wpf.Zen.Ui，交互验收通过 |
| P5：集成与清理 | 更新 Gallery、DI、示例、测试、文档；清除旧入口和重复资源 | 所有受影响目标框架构建通过，文档与实现一致 |

P1 是进入正式迁移的技术门槛。若多程序集系统资源方案不能可靠满足既有宿主能力，应先调整宿主设计与明确限制，再继续 P2/P3。

## 9. 验收矩阵

| 范围 | 必须验证的行为 |
| --- | --- |
| 项目依赖 | ThemeLib 无控件库引用；VirtualInput 无主库直接或传递依赖 |
| 单独使用 | 只使用 ThemeLib 的原生 WPF 自定义控件示例可正常切换主题 |
| 多模块 | 不同程序集私有键独立解析；共享键遵循明确覆盖规则 |
| 主题状态 | Light、Dark、System、高对比度进入/退出及系统颜色变化 |
| 强调色 | 系统、自定义、默认来源；使用不同生成规则的模块同步更新 |
| 局部主题 | 全局 Dark + 局部 Light；全局更新不覆盖局部选择 |
| 资源稳定性 | 普通调色板切换不替换模板，输入、焦点、Popup 状态保持 |
| 初始化 | 未初始化可用；控件先创建后激活管理器仍正确更新 |
| 错误路径 | 重复 ID、缺失/循环依赖、坏 URI、工厂失败不破坏现有资源 |
| 宿主 | Application、WinForms/ElementHost、无 Application、多 STA |
| 框架适配 | 系统主题重置、反射失败降级、资源图线程亲和性 |
| 键盘 | 候选滚动、工具按钮、图标、焦点不抢占、自动化及原有输入流程 |
| 打包 | net472 与 net8.0-windows；NuGet 依赖及打包后的 XAML URI 可用 |

测试聚焦资源查找、状态保持、依赖边界和宿主行为，不仅检查配置对象属性值。视觉及系统高对比度相关场景应包含人工验收记录。

## 10. 交付内容与实施原则

最终交付包括 ThemeLib 项目、模块注册与配置 API、资源键归属整理、独立 VirtualInput、更新后的主库集成、三个最小示例（仅主题、仅键盘、多风格模块）及必要测试。

公开 API、附加属性、模板契约、资源优先级、生命周期和反射适配须同步编写 XML 文档及关键实现注释。依赖属性定义紧邻 CLR 包装属性。注释描述当前契约，不叙述已删除实现的迁移历史。

实施顺序坚持先证明多模块与宿主机制，再迁移项目，最后解除控件依赖。最终边界是：ThemeLib 协调主题状态与资源，各控件库拥有自己的表现与风格。
